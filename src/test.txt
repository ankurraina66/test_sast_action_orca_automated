The safest fix is to encode user once, at the output, with the existing ServletUtil.sanitizeWeb. That covers both contexts on line 90. I modified no files.

1. Current vulnerable code (WebContent/admin/admin.jsp:89-91)

<% for (String user:users){ %>
<option value="<%=user%>"><%=user%></option>
<%} %>

2. Proposed replacement

<% for (String user : users) {
       String safeUser = ServletUtil.sanitizeWeb(user); %>
<option value="<%=safeUser%>"><%=safeUser%></option>
<% } %>
ServletUtil is already imported in this page (line 28). The username is encoded once and the result is reused in both places.

3. Why this works for both contexts

- Visible option text (HTML body): The characters that start markup, <, > and &, become entities. A username like <script>… renders as text instead of running.
- Attribute value (value="..."): The attribute is double-quoted, and escapeHtml converts " to &quot;. That stops a username from closing the attribute and adding onmouseover=… or similar.
- Form behavior is unchanged: The browser decodes entities in attribute values before submitting. The username parameter that reaches the servlet is the original raw value, so the add-account feature keeps working.

4. Concerns with using sanitizeWeb here

- It depends on the double-quoted attribute: Commons Lang 2 escapeHtml doesn't escape the single quote ', from my knowledge of that library. It's safe on this page because the attribute uses ". Don't reuse it for single-quoted attributes, JavaScript, URLs or CSS contexts.
- Library version is unconfirmed: ServletUtil.java:42 imports org.apache.commons.lang.StringEscapeUtils, which is Commons Lang 2. I found no commons-lang*.jar in the repo, so I couldn't confirm the exact version or the behavior above. The project also uses Lang 3's escapeHtml4 in notfound.jsp. Test with a username such as "><img src=x onerror=alert(1)> before relying on this.
- Null handling: escapeHtml(null) returns null, and JSP would print the string "null". USER_ID values from the database are unlikely to be null, so this is minor.
- Non-ASCII characters: Lang 2 turns characters like é into named entities. They still display correctly, so this only changes the page source.
- Don't use the other helper: sanitzieHtmlWithRegex in the same file is a pattern blocklist that returns an empty string on a match. A blocklist is weaker than encoding, so don't use it here.
- Rescan may still flag it: I can't say whether AppScan will recognize sanitizeWeb as an encoder. If the finding persists after a rescan, the fix may still be correct, and the issue would need review rather than more code changes.
- Double encoding: I haven't checked whether the servlet that receives username encodes it again. If it does, output elsewhere could show &amp;. This only matters for usernames containing special characters.

Alternative

The OWASP Java Encoder (Encode.forHtmlContent for the text, Encode.forHtmlAttribute for the attribute) is the more precise tool. It would add a dependency, which isn't worth it for this one page.
