Subject: Potential IRX source-coverage issue in Gradle projects

We investigated a completed SAST scan of the IntelliJ plugin project and found a potential mismatch in the MCP server's IRX preparation logic.

Observed results

- Project contains 126 Java source files under "src/main".
- Project contains 582 compiled ".class" files under "build".
- AppScan reported 12 Java files and 1,303 lines of code.
- The completed scan reported zero findings.
- The original generated IRX and preparation artifacts were deleted after upload, so we cannot inspect the exact contents of that IRX.

Relevant implementation evidence

In "tools/createScan.js", the server selects the preparation directory as follows:

const scanDir = fs.existsSync(buildDir) ? buildDir : targetDir;

The server generates "appscan-config.xml" for the project root. The existing configuration contains:

<Target path="C:\Users\ankur.raina\Downloads\impl_workspace\master_2.13.1\intellij-plugin">
  <CustomBuildInfo jdk_path="C:\Program Files\Java\jdk-25.0.2" additional_classpath="C:\Users\ankur.raina\Downloads\impl_workspace\master_2.13.1\intellij-plugin\build\libs"/>
  <Exclude>build/</Exclude>
</Target>

In "tools/scanService.js", "generateIRX()" passes the selected directory as the command working directory and invokes "appscan prepare" with the generated configuration file.

Concern

For this Gradle project, the configured target is the project root, while the preparation command's working directory is "build", which is also excluded by the configuration. This may affect discovery or interpretation of the intended source tree. We have not yet established that this is the definitive cause of the lower file count.

Request

1. Please confirm the intended semantics of the "-c" configuration target and relative exclusions when "appscan prepare" is executed from a different working directory.
2. Please review whether Gradle projects should use the project root as the preparation directory when the generated configuration targets that root.
3. For a controlled reproduction, please preserve the IRX and diagnostic artifacts (using the existing "conserveFiles" option where supported) and retain the preparation logs or "scan_logs.zip", including the manifests.
4. Compare the files discovered and included in the resulting IRX against the 126 Java source files in the project.

We have not changed the external server, modified the configuration, or rerun the scan. We would like to confirm the root cause before implementing a correction.

Acceptance criteria: a controlled reproduction demonstrates that the expected Java source files are included in the IRX, and the resulting AppScan scan reports coverage consistent with the intended source set.
