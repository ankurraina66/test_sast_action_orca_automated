**Targeting rules from the description**
- **Explicit target:** A target must be named explicitly. Use `issueId` for one issue, `appId` or `scanId` as shorthand, or `scope` plus `scopeId`.
- **No conflicting values:** Don't supply conflicting `scope`, `appId` and `scanId` values.
- **Filters:** `odataFilter` narrows the issues within the named scope. It never selects the target itself.

## 5. What issue data the tool can modify

- **Status:** Set to one of the seven enum values.
- **Comment:** Added to the updated issues.
- **External ID:** Set on the updated issues.
- **Scale:** One issue (via `issueId`), or every issue matching a filter in a scope. A broad scope such as a whole application with no filter could change many issues at once.
- **Comment-only updates:** AppScan can't store a comment without a status. A comment-only request therefore must send the issue's current status so the status doesn't change.
- **Result reporting:** The returned count covers status transitions only. A count of 0 doesn't mean failure, and the call must not be retried because of it.
- **Retries:** An identical repeat call is suppressed unless `allowDuplicate` is true, which would add the same comment a second time.

## 6. Preview and approval workflow

- **Approval:** The description says "Approval is required before changes."
- **Preview:** The `confirmToken` description refers to a preview flow, so a preview step appears to exist. The definition doesn't say what the preview shows.
- **After the call:** A successful response means the write was applied. The tool should report the target scope, issue IDs, the comment result and whether the status changed.
- **Mechanism:** The definition doesn't describe it in full. Approval comes through client elicitation, or through the `confirmToken` flow when elicitation isn't available.
