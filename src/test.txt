As a DevSecOps engineer or CI/CD pipeline operator,
I want to run SAST and SCA scans from the AppScan Cloud CLI,
So that I can identify source code vulnerabilities and vulnerable open-source dependencies directly from the command line or any CI/CD pipeline.

Business Context

Today the AppScan Cloud CLI only supports Dynamic Application Security Testing (DAST). Customers who want SAST or SCA capabilities must use other AppScan CICD plugins or the web console. This limits adoption in CI/CD environments where AppScan Plugins are not there (AWS CodePipeline, Bamboo, Google Cloud etc.) and prevents teams from running source-level security scans as part of automated build pipelines.

SAST and SCA are core pillars of a shift-left security strategy. Bringing these capabilities into the CLI will:

Provide a single, platform-agnostic tool for all three scan types (DAST, SAST, SCA)

Enable security gates in any CI/CD pipeline

Reduce manual effort and mean time to detect vulnerabilities

Support compliance requirements that mandate source-level and dependency-level scanning

Functional Requirements

FR-1: SAST Scanning Command (invokesastscan)

The CLI shall provide a new command invokesastscan that allows users to submit source code for static analysis. The command must support:

Authentication -- Users provide their AppScan on Cloud or AppScan 360 API key and secret. The CLI authenticates and verifies the user has an active SAST subscription before proceeding.

Two scan methods:

IRX Generation (default) -- The CLI downloads the SAClient locally, generates an IRX file from the source code, and uploads it to AppScan for analysis.

Direct Upload -- The CLI uploads source files, directories, or pre-built IRX files directly without local IRX generation.

Scan speed control -- Users can choose between normal, fast, faster, and fastest scan speeds, trading thoroughness for scan time.

Combined SAST + SCA analysis -- By default, the SAST command also performs Software Composition Analysis alongside static analysis, providing a unified view of both code-level vulnerabilities and vulnerable open-source dependencies. Users can disable this with an option.

Source-code-only mode -- Users can restrict analysis to source code only (no binary analysis). This mode is not available with the direct upload method.

Open-source-only mode -- Users can restrict analysis to open-source components only, effectively performing an SCA scan through the SAST command.

Rescan capability -- Users can rescan a previously submitted scan by providing the scan ID.

Application association -- Each scan is associated with a registered AppScan application via application ID.

FR-2: SCA Scanning Command (invokescascan)

The CLI shall provide a new command invokescascan that performs standalone Software Composition Analysis. The command must support:

Authentication & entitlement -- Same as SAST, but validates SCA subscription.

Dependency analysis -- Analyzes open-source and third-party libraries in the target directory for known CVEs.

Rescan capability -- Same as SAST.

Application association -- Same as SAST.

FR-3: Scan Results & Reporting

Both SAST and SCA commands must provide:

Real-time progress -- Display live scan status, elapsed duration, and progress percentage while a scan is in progress.

Findings summary -- Breakdown of findings by severity: Critical, High, Medium, Low, Informational, and total count.

Scan summary -- Application name, scan ID, scan name, creation timestamp, created-by details, target, and a direct URL to view the scan in the AppScan web console.

Report download -- Download the scan report to ./AppscanReports/ in the user's chosen format (HTML, PDF, CSV, or XML). Default is HTML.

Scan log download -- Download scan logs as a zip file to ./AppscanReports/.

FR-4: Build Gate / Quality Gate Integration

Both commands must support CI/CD quality gates:

Threshold-based failure (failbuildif subcommand) -- Allow users to set maximum thresholds on total, critical, high, medium, and low severity issues. If any threshold is exceeded, the CLI exits with a non-zero code. Conditions are OR'd.

Policy-based failure (--failBuildNonCompliance) -- Fail the build if any issues violate the compliance policies configured on the AppScan application.

Async mode (--waitForResults=false) -- Fire-and-forget usage where the scan is submitted but the CLI does not wait for results.

FR-5: AppScan 360 Support

Both commands must work with HCL AppScan 360 (on-premises) in addition to AppScan on Cloud (SaaS):

Accept a custom service URL (--serviceUrl)

Accept untrusted SSL certificates (--acceptssl) for development/testing environments

API keys for AppScan 360 use the local_ prefix convention

FR-6: CLI Help & Discoverability

Running the CLI with --help must list invokesastscan and invokescascan alongside the existing invokedynamicscan command.

Each new command must display comprehensive help text with option descriptions and defaults.

The CLI header must reflect all three scan types (DAST, SAST, SCA).

Non-Functional Requirements

Platform agnostic -- Must work on any OS where Java 11+ is available (Linux, macOS, Windows).

No CI/CD platform dependency -- Pure CLI executable; no Jenkins or other platform dependency.

Backward compatibility -- Existing invokedynamicscan, getapplications, and getpresenceids commands must continue to work without any behavioral change.

SDK compatibility -- Must use AppScan SDK v1.1.12 or later.

Supply chain security -- All dependency versions (direct and transitive) must be pinned and locked per SCAL-PKGDEP-2 requirements.

Consistent UX -- SAST and SCA commands must follow the same option naming conventions, output format, and scan lifecycle as the existing DAST command.

Example Usage Scenarios

Scenario 1 -- Nightly SAST scan in a AWS pipeline
A team runs a full SAST+SCA scan every night against the main branch, failing the build if any critical issues are found.

Scenario 2 -- PR-level SCA gate in GitHub Actions
On every pull request, an SCA scan checks for newly introduced vulnerable dependencies, blocking merge if critical CVEs are detected.

Scenario 3 -- Release gate with policy compliance
Before a production release, a SAST scan is run with --failBuildNonCompliance=true to ensure no findings violate the application's security policy.

Scenario 4 -- Fire-and-forget scan submission
A developer submits a scan with --waitForResults=false and reviews results later in the AppScan web console.

Scenario 5 -- AppScan 360 on-premises scanning
An enterprise team runs SAST scans against their AppScan 360 on-premises instance using --serviceUrl and --acceptssl.

Acceptance Criteria (Epic-Level)

A user can run invokesastscan with valid credentials and a source code directory to successfully submit a SAST scan and receive findings categorized by severity.

A user can run invokescascan with valid credentials and a source code directory to successfully submit an SCA scan and receive dependency vulnerability findings.

The SAST command supports both IRX generation and direct upload scan methods.

The SAST command includes SCA analysis by default; users can disable it.

Both commands download a scan report (HTML/PDF/CSV/XML) and scan logs to ./AppscanReports/ upon completion.

The failbuildif subcommand correctly fails the build (exit code 10) when any configured severity threshold is exceeded.

The --failBuildNonCompliance option correctly fails the build (exit code 12) when non-compliant issues exist.

Users without a valid SAST or SCA subscription receive a clear error message and the scan is not submitted.

Users without SCA entitlement in a combined SAST+SCA scan receive a warning and the scan proceeds without SCA (graceful degradation).

The --rescan option with --scanId correctly performs a rescan of an existing scan.

Real-time progress display shows scan status, duration, and progress during execution.

Both commands work with AppScan on Cloud (SaaS) and AppScan 360 (on-premises with --serviceUrl).

The --help output for the main CLI and each new command is complete and accurate.

Existing DAST functionality is unaffected.

The CLI builds successfully, passes lockfile validation, and all existing tests continue to pass.

Dependencies

HCL AppScan SDK v1.1.12 (provides SAST/SCA scan factories and entitlement APIs)

Active SAST and/or SCA subscription on AppScan on Cloud or AppScan 360 for end-to-end testing

Risks & Considerations

SAClient dependency -- The IRX generation scan method requires the SAClient to be downloaded and executed locally. Users behind restrictive firewalls may need to use the direct upload method instead.

Combined results handling -- When SAST + SCA are run together, the backend returns combined results. The CLI must correctly aggregate and display findings from both scan types.

Scan duration -- SAST scans on large codebases can take significant time. The async mode (--waitForResults=false) mitigates this for pipelines with time constraints.

Entitlement mismatches -- A user may have SAST but not SCA entitlement. The CLI should gracefully degrade combined scans rather than failing outright.
