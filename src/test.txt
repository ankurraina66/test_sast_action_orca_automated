Summary
Optimized the vulnerability summary generation logic by replacing client-side issue retrieval and aggregation with the AppScan Issues API server-side aggregation capability using OData groupby and aggregate($count). This eliminates the need to retrieve all issues or implement pagination solely for severity count calculation.

Implementation Details
Updated the Issues API request to use OData grouping:

ApplyPolicies = All

Filtered only actionable issue statuses (Open, InProgress, Reopened, New)

Applied groupby((Status,Severity),aggregate($count as N)) to retrieve aggregated counts directly from the server.

Removed the dependency on fetching individual issue records for summary generation.

Parsed the grouped API response and accumulated counts for each severity level (Critical, High, Medium, Low, Informational).

Calculated the total vulnerability count by summing the aggregated severity counts.

Preserved the existing GitHub Build Summary and PR Summary format without functional changes.

Added temporary diagnostic logging to capture:

Grouped Issues API request URL

Raw grouped API response

Number of grouped records returned

Status/Severity-wise aggregated counts

Final calculated severity totals

Benefits
Eliminates the need for pagination while generating vulnerability summaries.

Significantly reduces network traffic by retrieving only aggregated data instead of every issue.

Improves performance and memory utilization, especially for scans containing a large number of vulnerabilities.

Simplifies the implementation by leveraging AppScan's native server-side aggregation capabilities.

Maintains identical summary output while reducing API processing overhead.

Validation Performed
Successfully validated against SAST and SCA scans.

Verified that the grouped API response returns the expected severity-wise counts.

Confirmed that the calculated totals match the values displayed in the GitHub Build Summary.

Verified that hyperlinks, scan metadata, and summary generation continue to function as expected after the implementation changes.
